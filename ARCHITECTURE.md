# Architecture

This document explains how **NYC Subway Editor** is put together: what each file does, how data moves from JSON on disk to colored lines on a map, and the rendering tricks that make shared track, transfers, and station dots look right. It also records the project's current limits and the gotchas worth knowing before you change anything.

> **Status (Nov 2026):** the app is a **viewer** of the current NYC subway that can also overlay **proposed lines**. So far the Second Avenue Subway (Q extension + new T), the Interborough Express (IBX), the Utica Avenue 4 extension, the Red Hook W extension, the Nostrand Avenue 2 extension, and the Flatbush Avenue 5 extension have data. Only Queenslink is still empty. Editing and file upload are not built yet. See [Current state and gaps](#current-state-and-gaps).

## What the app does

- A landing page (`/`) offers two choices: **Use Current Subway Map** or **Upload File** (the upload button does nothing yet).
- The map page (`/map`) shows a full-screen interactive map of the NYC subway:
  - Every line drawn in its official MTA color. Routes that share track run **side by side** as parallel lanes instead of on top of each other.
  - A white dot with a dark outline at every stop. The dot grows with the number of parallel lanes it sits on.
  - **Transfer connectors** (a white core with a dark outline) between platforms in the same station complex, such as Times Sq–42 St and 42 St–Port Authority.
  - Faint **borough outlines** under the lines.
  - **Hover** a stop: a tooltip with its name, an ADA icon if it is accessible, and the route bullets that stop there.
  - **Click** a stop: a popup with name, borough, accessibility details, trains, and in-station transfers grouped by platform.
  - A collapsible **legend** ("Lines") in the bottom-left with bullets grouped by line color.
  - A collapsible **Proposed Lines** panel in the top-right. Checking a line merges it into the map: new stops, track, transfers, bullets, and a legend entry. Unchecking removes it again. Your current pan and zoom are kept.
  - Panning is fenced to NYC, and you cannot zoom out past the point where NYC fills the screen.

## Routes and pages

### `/` — [src/app/page.js](src/app/page.js)

A static Server Component. It renders the title, a subtitle, and two actions:

- **Use Current Subway Map**: a `next/link` to `/map`.
- **Upload File**: a `<button type="button">` with **no handler**. It is a placeholder for loading a user's own map document.

### `/map` — [src/app/map/page.js](src/app/map/page.js) + [src/components/MapView.js](src/components/MapView.js)

**`page.js`** is a thin Server Component. It imports `map.json`, `boroughs.json`, and `proposed.json` (bundled at build time; nothing is fetched at runtime), sets the page title, and renders `<MapView baseMap proposals boroughs />`.

**`MapView.js`** is a Client Component (`"use client"`) that owns the screen:

1. **State:** `enabled`, a `Set` of the proposal names that are checked. It starts empty, so the map first shows the current subway.
2. **Derived data** (each in a `useMemo`):
   - `map = applyProposals(baseMap, enabled proposals)`. Proposals are applied in **file order**, not click order, so the result is deterministic. With nothing checked, `applyProposals` returns `baseMap` itself.
   - `{ stops, segments, transfers } = buildNetwork(map)`.
   - `legend = buildLegend(map)`: one row per color that has routes, in `map.colors` order, with de-duplicated bullets.
3. **Renders:**
   - `<SubwayMap stops segments transfers boroughs />`, which fills the viewport (`h-dvh`).
   - A floating **header** (top-left): a "← Back" link, the title, and a station count (`map.stations.length`: 445 for the base map, 452 with the Second Avenue Subway on, 450 with the IBX on, 452 with the Utica extension on, 448 with Red Hook on, 451 with Nostrand on, 449 with Flatbush on, 475 with all six).
   - A floating **Proposed Lines** panel (top-right, `w-64`): a native `<details>` that starts **collapsed**. Its `+` icon rotates to `×` when open. It has one **controlled** checkbox per key of `proposed.json`, in file order. Toggling a box adds or removes its name in `enabled`. Proposals with an empty `{}` value can be checked but change nothing. The panel sits at the top-right corner, clear of the zoom control at the bottom-right.
   - A floating **legend** (bottom-left): a native `<details open>`. Each row shows a color swatch followed by `next/image` bullets. It is built from the merged map, so a checked proposal's new routes (e.g. the teal **T** and the pink **IBX**) appear in it.

Overlays use `z-[1000]` so they sit above Leaflet's panes (Leaflet uses z-indexes up to about 800). The header wrapper is `pointer-events-none` and only its inner card is `pointer-events-auto`, so the empty strip across the top still lets you drag the map.

The page is still **prerendered statically** (no cookies, headers, or params). During prerender `MapView` renders with nothing checked, so `buildNetwork` runs at build time for the initial HTML, then again in the browser on hydration and on every toggle. The raw `map.json`, `proposed.json`, and `boroughs.json` are serialized into the RSC payload as `MapView` props.

### Root layout — [src/app/layout.js](src/app/layout.js)

- Loads the Geist and Geist Mono fonts and exposes them as `--font-geist-sans` / `--font-geist-mono`.
- Sets site metadata: title "NYC Subway Editor". `/map` overrides the title with "Current Subway Map · NYC Subway Editor".
- `<html class="h-full antialiased">` and `<body class="min-h-full flex flex-col">` let pages use `flex-1` or `h-dvh` to fill the screen.

## End-to-end data flow

```
            SERVER / BUILD                                       BROWSER
 ┌───────────────────────────────┐   ┌───────────────────────────────────────────────────────────────┐
 │ app/map/page.js               │   │ MapView ("use client")                                        │
 │                               │   │                                                               │
 │  map.json      ── baseMap ────┼──►│  enabled: Set<name> ◄── Proposed Lines checkboxes             │
 │  proposed.json ── proposals ──┼──►│        │                                                      │
 │  boroughs.json ── boroughs ───┼─┐ │        ▼                                                      │
 │                               │ │ │  applyProposals(baseMap, checked proposals)  (lib/proposals)  │
 └───────────────────────────────┘ │ │        │  merged map document                                │
                                   │ │        ├──► buildLegend()  ──► Legend <details>              │
                                   │ │        └──► buildNetwork() (lib/network)                      │
                                   │ │                 │ stops[] (+ bullets, transfers)              │
                                   │ │                 │ segments[] (from, to, colors[])             │
                                   │ │                 │ transfers[] ([id, id])                      │
                                   │ │                 ▼                                             │
                                   └─┼──────────► SubwayMap ("use client")                           │
                                     │              effect 1 (once):  import("leaflet"), L.map,      │
                                     │                 pan fence, Esri tiles ◄── internet,           │
                                     │                 borough outlines, shared canvas renderer      │
                                     │              effect 2 (per network): layerGroup of lanes,     │
                                     │                 transfer connectors, stop dots + tooltip/popup│
                                     │                 HTML, redraw() on every zoomend               │
                                     └───────────────────────────────────────────────────────────────┘
```

The rule of thumb:
- **`network.js` and `proposals.js` are pure data.** They know nothing about Leaflet, React, or pixels.
- **`SubwayMap.js` is pure presentation.** It knows nothing about the raw `map.json` format, only the shapes `buildNetwork` returns.
- **`MapView.js` is the glue.** It holds UI state and turns it into a network.

## The map document (`map.json`)

[src/data/map.json](src/data/map.json) is the single source of truth for the network. Commit `ad76c1d` merged earlier separate files into this one document, so the app could later load an uploaded file of the same shape.

### Top-level shape

```jsonc
{
  "name": "NYC Subway",
  "description": "Current daytime subway service.",
  "colors":   [ /* 11 */ ],
  "routes":   [ /* 26 */ ],
  "stations": [ /* 445 */ ],
  "stops":    [ /* 496 */ ]
}
```

`name` and `description` are not read by any code yet.

### `colors[]` — `{ id, hex }`

```json
{ "id": "blue", "hex": "#0039A6" }
```

The 11 colors, **in file order**: `blue, orange, lime, brown, gray, yellow, red, green, purple, shuttle, sir`.

**The array order matters.** It sets:
1. The **left-to-right order of lanes** on shared track. A segment's colors are sorted by their index in this array (see [Segments](#segments)).
2. The **row order of the legend**.

### `routes[]` — `{ id, bullet, name?, color, paths }`

```json
{ "id": "A",  "bullet": "A", "color": "blue", "paths": [["A02", "A03", ...], ["A61", "H01", ...]] }
{ "id": "GS", "bullet": "S", "name": "42 St Shuttle", "color": "shuttle", "paths": [["902", "901"]] }
```

| Field | Meaning |
|---|---|
| `id` | Unique route key. Stops refer to it in `stop.routes`. Usually the same as the bullet; the shuttles use `GS`, `FS`, `H`; Staten Island uses `SIR`. |
| `bullet` | Display label, and the image file name (`bullet.toLowerCase() + ".png"`). The three shuttles all use `S`. |
| `name` | Optional long name. Only shuttles and SIR have one. Not shown anywhere yet. |
| `color` | A `colors[].id`. |
| `paths` | One or more **ordered lists of stop ids** along the track. Each consecutive pair becomes a track segment. Use more than one path for branches. |

The routes: `1 2 3 4 5 6 7 A C E B D F J Z M G L N Q R W GS FS H SIR`. Only **A** has two paths: the trunk to Ozone Park–Lefferts Blvd, and a branch from Rockaway Blvd (`A61`) to Far Rockaway (`H01…H11`).

Paths describe **track geometry and service**. They are not timetables: a route that runs express through a stop simply leaves that stop out of its path.

### `stations[]` — `{ id, name, stops }`

```json
{ "id": "611", "name": "Times Sq-42 St / 42 St-Port Authority Bus Terminal", "stops": ["R16", "A27", "127", "725", "902"] }
```

A **station** groups stops that are **connected in-system** (free transfer). Every stop belongs to exactly one station.

- 445 stations. **35** have 2 or more stops; the largest is Times Sq with 5.
- Ids look like MTA identifiers: single-platform stations use plain station numbers (`"1"`, `"2"`, …), and multi-platform complexes use complex numbers (`"601"`, `"611"`, …).
- `station.name` is not shown in the UI. The UI uses the **stop** name.

### `stops[]` — `{ id, name, borough, lat, lng, routes, accessibility, accessibilityNote? }`

```json
{ "id": "R15", "name": "49 St", "borough": "Manhattan", "lat": 40.759901, "lng": -73.984139,
  "routes": ["N", "R", "W"], "accessibility": "partial", "accessibilityNote": "Uptown only" }
```

A **stop** is one platform group (one GTFS parent stop). It is the unit that gets a dot on the map.

| Field | Meaning |
|---|---|
| `id` | GTFS-style stop id (`R01`, `A27`, `127`, `902`, …). Must be unique. Referenced by `routes[].paths` and `stations[].stops`. |
| `name` | Display name. Several stops can share a name, e.g. the four "Canal St" platforms. |
| `borough` | Free text shown in the popup: `Manhattan`, `Brooklyn`, `Queens`, `The Bronx`, `Staten Island`. |
| `lat`, `lng` | WGS84 coordinates. |
| `routes` | Route ids that **stop here**. Drives the bullets in the tooltip and popup. This list is **separate from `paths`** (see [Gotchas](#gotchas-and-invariants)). |
| `accessibility` | `"full"` (166 stops), `"partial"` (8), or `"none"` (322). |
| `accessibilityNote` | Only on partial stops, e.g. `"Uptown only"`, `"Manhattan-bound only"`. |

Counts by borough: Brooklyn 169, Manhattan 153, Queens 83, The Bronx 70, Staten Island 21. Total 496.

### Integrity of the current data (checked)

- Every stop id in a route path exists in `stops`.
- Every stop belongs to a station.
- Every id in `stop.routes` is a real route.
- Three pairs of stops share exact coordinates: `A12`/`D13`, `A32`/`D20`, `R09`/`718`. `buildNetwork` skips zero-length transfer links for them.

## Supporting data

### `boroughs.json`

A GeoJSON `FeatureCollection` with 5 `MultiPolygon` features. Each has `properties: { name, code }`, where `code` is the NYC borough code `1`–`5`. Commit `b391024` notes the source as simplified NYC Open Data. It has two uses:
1. Drawing the faint outlines.
2. Computing the **pan fence**: the outlines' bounding box, padded 15%.

Note: the feature is named `"Bronx"`, but stops use `"The Bronx"`. Nothing joins the two today.

### `proposed.json` and `applyProposals`

[src/data/proposed.json](src/data/proposed.json) is an **object keyed by proposed line name**. The key is the label shown in the Proposed Lines panel. Each value is a **fragment of a map document** that [src/lib/proposals.js](src/lib/proposals.js) merges onto `map.json` when the line is checked. Because the result has exactly the `map.json` shape, `buildNetwork`, the legend, and `SubwayMap` need no special cases for proposals.

```jsonc
{
  "Second Avenue Subway": {
    "colors":   [{ "id": "teal", "hex": "#00ADD0" }],
    "routes":   [
      { "id": "Q", "paths": [["T01", ..., "T06", "Q05"]] },                        // existing id → extends the Q
      { "id": "T", "bullet": "T", "color": "teal", "paths": [["T01", ..., "T16"]] } // new id → new route
    ],
    "stops":    [{ "id": "T01", "name": "125 St & Broadway", "borough": "Manhattan",
                   "lat": 40.8158, "lng": -73.9584, "accessibility": "full" }, ...],
    "stations": [{ "id": "610", "stops": ["T08"] }, ...]                               // join existing complexes
  },
  "Interborough Express (IBX)": { /* same shape: pink IBX route, stops X01–X18 */ },
  "Utica Avenue Extension": { /* extends route 4 from 250, stops U01–U07 */ },
  "Redhook Extension":      { /* extends route W from R27, stops W01–W03 */ },
  "Nostrand Avenue Extension": { /* extends route 2 from 247, stops V01–V06 */ },
  "Flatbush Avenue Extension": { /* extends route 5 from 247, stops K01–K04 */ },
  "Queenslink": {}
}
```

**Merge rules** (`applyProposals(base, proposals[])`). Every field is optional, and `{}` changes nothing.

| Field | Rule |
|---|---|
| `colors` | Appended after the base colors, skipping ids that already exist. Appending puts new colors **last** in lane order and legend order. |
| `routes` | **New id** → added as a new route. **Existing id** → its `paths` are **added** to that route. This is how a proposal extends an existing line. |
| `stops` | New stops only (an existing id is skipped). **No `routes` field**: see the service rule below. `accessibility` defaults to `"none"`. |
| `stations` | **Existing id** → the listed stops join that station, which creates in-system transfers and connectors. **New id** → a new station. Listing a stop that **already belongs to another station** merges that whole station in (its id disappears), so two existing stations can be joined into one complex. The IBX uses this at Livonia Av. |
| Service rule | Every stop on a proposal route's paths gets that route id added to its `routes`. Proposal paths must therefore list **only the stops the route serves**. This is also how existing stops pick up new bullets (e.g. 72, 86 and 96 St gain the T). |
| Missing stop ids | After all proposals are applied, station stop ids that don't exist are dropped, and stations left empty are removed. This lets a proposal declare a **transfer to another proposal's stop**: it only appears when both are checked, and it works in either file order. The Utica extension uses this for the IBX. |
| Leftover stops | Any new stop not placed in a station gets a single-stop station of its own (id = stop id). |

The base document is **never mutated**: routes, stations and stops are shallow-copied with fresh `paths`, `stops` and `routes` arrays. With no proposals it returns `base` itself.

Ordering details:
- Within a proposal, list routes in the order their **bullets should appear** on new stops. The SAS lists `Q` before `T`, so new stops show "Q T".
- Proposal paths are processed **after** all base routes, so base segments keep their direction (see [Segments](#segments)). Proposal paths should run in the same direction as base routes on shared track to avoid flipping lane sides. The SAS paths run north → south like the Q.

## `buildNetwork`: from document to drawable network

[src/lib/network.js](src/lib/network.js). A pure function with no side effects outside its own objects.

```js
buildNetwork(map) → { stops, segments, transfers }
```

### Lookup tables (lines 11–14)

| Map | Key → value |
|---|---|
| `colorHex` | color id → hex |
| `colorRank` | color id → index in `map.colors` (lane order) |
| `bulletOf` | route id → bullet label |
| `stationOf` | stop id → the station object that contains it |

### Stops (lines 16–28)

Each raw stop becomes:

```js
{
  id, name, borough, lat, lng,
  bullets: ["N", "W"],              // stop.routes mapped through bulletOf (GS/FS/H → "S")
  accessibility: "full" | "partial" | null,   // "none" is normalized to null
  accessibilityNote: string | null,
  transfers: [{ name, bullets }],   // added by addStopTransfers()
}
```

### Per-stop transfers: `addStopTransfers` (lines 64–79)

For every stop, it looks at the **other stops in the same station** and works out which **new** bullets you can reach:

1. Start a `seen` set with the stop's own bullets.
2. For each other stop in the station (in `station.stops` order), keep only the bullets not yet seen, and add them to `seen`.
3. Group the remaining bullets by the **other stop's name**.

So at Times Sq on the 1/2/3 platform you get:
```js
[{ name: "Times Sq-42 St", bullets: ["N","Q","R","W","7","S"] },
 { name: "42 St-Port Authority Bus Terminal", bullets: ["A","C","E"] }]
```
A bullet is listed only once, under the first platform that offers it. Platforms that add no new bullets are left out.

This function **mutates** the stop objects to add `transfers`. That is safe because the stop objects were just created on lines 16–26.

### Segments (lines 30–52)

A segment is **one stretch of track between two adjacent stops**, shared by every route that runs over it.

1. For every route, every path, and every consecutive pair `(from, to)`, build the key `min|max` (string comparison), so A→B and B→A are the same segment.
2. The **first path to create a segment fixes its `from`/`to` direction.** This matters because lane offsets are computed relative to the segment's direction. A fixed direction keeps a color on the same side of the bundle no matter which route is drawn.
3. Collect the **color ids** (not route ids) seen on the segment. This means **routes of the same color share one lane**: N, Q, R, and W on the same track are a single yellow line. A segment with orange and blue gets two lanes.
4. Sort each segment's colors by `colorRank` and turn them into hex codes.

Output:
```js
{ from: "R16", to: "R17", colors: ["#FCCC0A"] }
{ from: "213", to: "214", colors: ["#EE352E", "#00933C"] }   // red (2) + green (5) share track in the Bronx
```

With the current data this produces **505 segments**. No segment carries more than **3** colors.

Pairs where either stop id is missing are silently skipped (line 38).

### Transfer links: `buildTransferLinks` (lines 83–105)

For every station with 2 or more stops, it draws connectors between the platforms. Joining every platform to the first one would look like a star. Instead it builds a **minimum spanning tree** with Prim's algorithm, measuring distance as squared Euclidean distance in raw lat/lng. That is good enough at city scale. The result is a tidy chain of links.

- Output: an array of `[stopIdA, stopIdB]` pairs.
- Links of zero length (stops at identical coordinates) are not emitted. The stops are still added to the tree.
- Cost is O(n³) per station, which is trivial for n ≤ 5.
- With the current data this produces **48 transfer links** across the 35 multi-stop stations.

## `SubwayMap`: rendering with Leaflet

[src/components/SubwayMap.js](src/components/SubwayMap.js). A Client Component (`"use client"`) that renders one `<div>` and does everything else imperatively with Leaflet inside a single `useEffect`.

### Lifecycle

The component renders one `<div>` and uses **two effects**:

```
mount
 ├─ effect 1 — create the map            deps: [boroughs]  (runs once in practice)
 │    import("leaflet")                  // dynamic: Leaflet touches `window` on import, so it can't load on the server
 │     └─ if unmounted already (cancelled) or no container → bail
 │     └─ L.map, view limits, tiles, borough outlines, shared canvas renderer
 │     └─ setLeaflet({ L, map, renderer })
 │    cleanup: cancelled = true; map?.remove()
 │
 └─ effect 2 — draw the network          deps: [leaflet, stops, segments, transfers]
      if !leaflet → wait
      L.layerGroup() ← lanes, transfer connectors, stop dots (+ tooltips/popups)
      map.on("zoomend", redraw); redraw()
      cleanup: map.off("zoomend", redraw); layerGroup.remove()
```

- `leaflet/dist/leaflet.css` is imported statically at the top of the file. CSS is safe to import during SSR.
- The `cancelled` flag guards against React 19 Strict Mode's mount → unmount → mount in development, and against fast navigation away from the page.
- **Toggling a proposed line** gives `SubwayMap` new `stops`, `segments`, and `transfers` arrays. Only effect 2 re-runs: the old layer group is removed (closing any open popup) and a new one is drawn. The map, tiles, and **the user's pan and zoom are kept**.
- The **initial view** is fitted to the stops from the first render, held in `initialStops` (a ref), so later networks never re-fit the view.

### Map setup (effect 1)

| Setting | Why |
|---|---|
| `panBounds = geoJSON(boroughs).getBounds().pad(0.15)` | The NYC bounding box plus 15% on each side. |
| `maxBounds: panBounds`, `maxBoundsViscosity: 1` | Panning stops hard at the fence, with no rubber-banding. |
| `zoomSnap: 0.25` | Quarter-step zooms, so the zoom-out limit can fit NYC closely. |
| `setMinZoom(getBoundsZoom(panBounds))`, recomputed on `resize` | You cannot zoom out past the point where the fenced area fills the viewport. |
| `fitBounds(all stops, padding 24)` | Initial view. |
| `zoomControl: false` + `L.control.zoom({ position: "bottomright" })` | Moves the zoom buttons out of the header's corner. |
| `preferCanvas: true`, `maxZoom: 18` | Canvas rendering; zoom allowed beyond native tiles. |
| Esri tile layers with `maxNativeZoom: 16` | Light-gray base, plus a separate label (reference) layer on top. Above zoom 16 the z16 tiles are scaled up. |

`fitBounds` is called **before** any vector layers are added, because canvas layers need the map to have a view first (see the comment on line 92).

### Layer stack (drawn in this order, bottom to top)

All vector layers share **one `L.canvas` renderer** (`padding: 0.5`, `tolerance: 6`). The 6 px tolerance makes the small stop dots easier to hover and click.

1. **Tiles:** Esri base, then Esri labels.
2. **Borough outlines:** `#525252`, 1.5 px, 70% opacity, no fill, not interactive. Added in effect 1, before any network layers, so they always sit underneath.

Everything below lives in effect 2's single `L.layerGroup`, which is replaced as a unit when the network changes:

3. **Track lanes:** one `L.polyline` per segment per color, not interactive.
4. **Transfer connectors:** for each link, a dark `#1a1a1a` "outline" polyline with a white "core" polyline on top. Not interactive.
5. **Stop dots:** `L.circleMarker`, white fill, `#1a1a1a` stroke. These are the **only interactive** layers.

### Parallel lanes (effect 2)

For a segment with `n` colors, color `i` gets the **slot** `i − (n − 1) / 2`:

| n | slots |
|---|---|
| 1 | 0 |
| 2 | −0.5, +0.5 |
| 3 | −1, 0, +1 |

On every redraw, each lane with a non-zero slot is shifted sideways in **screen pixels**:

```
pa, pb   = project(a), project(b)                  // lat/lng → pixel coords at current zoom
(nx, ny) = unit normal of (pb − pa) × slot × w     // perpendicular offset; w = line weight
line     = [unproject(pa + n), unproject(pb + n)]  // back to lat/lng
```

The offset equals one line width per slot, so lanes touch without overlapping at every zoom level. The offset is computed **per segment**, not along the whole route. Where the track bends there can be small seams between adjacent offset segments; the `lineCap/lineJoin: "round"` settings hide most of them.

### Zoom-dependent sizing: `redraw()` (effect 2)

`redraw` runs once at start and on every `zoomend`. It does not run continuously during the zoom animation.

| Thing | Formula |
|---|---|
| Line weight `w` | `clamp((zoom − 9) × 1.25, 2, 7)` px |
| Lanes | Recompute offsets (above), `weight = w` |
| Transfer outline | `w × 1.4` |
| Transfer core | `max(1, w × 1.4 − 3)`, which leaves about 1.5 px of dark outline on each side |
| Stop dot radius `r` | `max(0.75w, n·w / 2)`, where `n` is the widest bundle touching the stop (`lanesAt`, lines 124–129). The dot always covers every lane passing through it. |
| Dot stroke | 1.5 px at zoom ≥ 12, otherwise 1 px |
| Tooltip offset | `[0, −r]`: sits on the dot's top edge |
| Popup offset | `[0, 7 − r]`: Leaflet's default is `[0, 7]`; this lifts it to the dot's top edge. An open popup is `update()`d so it moves too. |

### Tooltips and popups

Leaflet tooltips and popups take **HTML strings**, so the content is built with template strings. These helpers use plain `<img>` tags, not `next/image`:

| Helper | Output |
|---|---|
| `bulletHtml(b)` | `<img class="route-bullet" src="/b.png">` |
| `bulletsHtml(bs)` | A row of bullets in `.station-tip-routes` |
| `accessibilityLabel(s)` | `"Accessible"`, `"Accessible: Uptown only"`, or `null` |
| `nameHtml(s)` | `.station-tip-name` with the stop name and the ADA icon if accessible |
| `stationPopupHtml(s)` | Name, then "Borough · Accessibility", then a **Trains** section, then a **Transfers** section (only if there are any). Each transfer row shows bullets and, **only if the platform's name differs** from this stop's, a `.station-popup-via` label. |

- Tooltip: `direction: "top"`, `className: "station-tip"`, opacity 1.
- Popup: `className: "station-popup"`, no close button, `autoPanPadding: [24, 24]`.
- When a popup opens, the tooltip is closed (`popupopen` → `closeTooltip()`), because the popup already repeats the tooltip's content.

## Gotchas and invariants

1. **`stop.routes` and `route.paths` are independent.** `stop.routes` controls the **bullets shown** at a stop. `route.paths` controls the **lines drawn**. If you add a route to a path but not to the stop's `routes`, the line will run through the stop without its bullet (and vice versa). Keep them in sync.
2. **Lanes are per color, not per route.** Two routes of the same color on the same segment are drawn as **one** line. To show them separately, give them different color ids.
3. **The order of `colors` is visual.** Reordering it changes which side of a shared-track bundle each line sits on, and the legend order.
4. **Segment direction comes from whichever path first creates the segment** (route order, then path order). Reordering `routes` can flip which side lanes appear on for some segments.
5. **Every stop must be in exactly one station** for transfers to work. A stop in no station gets `transfers: []` and no connectors. A stop listed in two stations would only be found in the last one, because `stationOf` keeps the last match.
6. **Bullet images must exist** at `/public/<bullet lowercase>.png`. A new bullet label without an image shows a broken image.
7. **Tooltip and popup HTML is not escaped.** Stop names, borough names, and accessibility notes are put straight into HTML. That is fine for the bundled `map.json`, but **once Upload File exists, uploaded data must be escaped or sanitized** to avoid XSS.
8. **Leaflet must stay browser-only.** Keep the dynamic `import("leaflet")` inside `useEffect`. A top-level `import L from "leaflet"` in any module that is rendered on the server will crash, because Leaflet reads `window`.
9. **Overlay z-index:** anything floating over the map needs `z-index > ~800` (the project uses `1000`), or Leaflet panes will cover it.
10. **The borough name mismatch** (`"The Bronx"` in stops vs `"Bronx"` in GeoJSON) is harmless today but will bite any feature that joins the two.
11. **Offsets update only on `zoomend`.** During the zoom animation, lanes are scaled with the old offsets, then snap into place. This is expected.
12. **Big payload:** the raw `map.json` (~145 KB), `proposed.json`, and `boroughs.json` (~164 KB) are all serialized into the page's RSC payload as `MapView` props. If these grow, consider simplifying the GeoJSON further or loading it from `/public`.
13. **Proposal paths must list only the stops served** (see the service rule in [`proposed.json`](#proposedjson-and-applyproposals)). Putting a stop in a proposal path adds that route's bullet to the stop, even if it's an existing stop.
14. **Proposal stop ids must not collide** with base stop ids (or each other). A duplicate id is silently skipped, and the route's path would then point at the existing stop. SAS uses `T01`–`T16`, IBX `X01`–`X18`, Utica `U01`–`U07`, Red Hook `W01`–`W03`, Nostrand `V01`–`V06` (`N` is taken by base stops), and Flatbush `K01`–`K04`; pick a distinct prefix for each new proposal.
15. **Proposals are applied in file order**, so a later proposal can extend routes, stops, or stations added by an earlier one, but not the other way round.

## How to extend

### Add or change a station / stop

1. Add the stop to `stops[]` with a unique `id`, `lat`/`lng`, `borough`, `routes`, and `accessibility`.
2. Add its id to a station in `stations[]`, either a new one-stop station or an existing complex.
3. Insert its id at the right place in each relevant `route.paths` list.

### Add a route

1. If it needs a new color, add `{ id, hex }` to `colors[]` at the position where its lane should sit.
2. Add `{ id, bullet, color, paths }` to `routes[]`.
3. Add `public/<bullet>.png`.
4. Add the route id to `routes` on every stop it serves.

### Make the network come from somewhere other than the bundled file

`buildNetwork` only needs an object with the `map.json` shape. A future upload or editor flow could:
- Parse and validate the uploaded JSON on the client, then call `buildNetwork` in the browser. It is pure, with no Node APIs. Then pass the result to `<SubwayMap>`. (`MapView` already does this for base + proposals; an upload could simply replace `baseMap`.)
- `SubwayMap` keeps the map and only redraws its network layer group when `stops`, `segments`, or `transfers` change, so swapping in a new network keeps the view. For very frequent live edits, consider updating individual Leaflet layers instead of redrawing the whole group.
- Escape all strings from user data before they reach the tooltip and popup HTML (see gotcha 7).

### Add a proposed line

Fill in (or add) its entry in `proposed.json` using the [merge rules](#proposedjson-and-applyproposals):

1. If it is a new service, add a color to `colors` and a route with `id`, `bullet`, `color`, and `paths`. Add `public/<bullet>.png` if that bullet doesn't exist yet.
2. To extend an existing service, add a route with only the existing `id` and the new `paths`. Each path must connect to an existing stop so the line joins up (e.g. the Q extension ends at `Q05`).
3. Add new stops with a unique id prefix. Leave out `routes`; they come from the paths.
4. For transfers, add `{ "id": "<existing station id>", "stops": [<new stop ids>] }` to `stations`. Find station ids by searching `map.json` for the stop you want to connect to. If the new stop should connect two stations that are separate today, also list a stop from the second station; that station is merged in. To connect to **another proposal's** new stop, create a new station listing both stop ids; it only takes effect when both proposals are on.
5. Reuse existing stop ids in paths where the proposal serves an existing station, instead of creating duplicates.

No code changes are needed: the panel lists the key, and the merged line appears on the map and in the legend when checked.
